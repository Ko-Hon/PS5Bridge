# 工作原理与实现范围

## 数据路径

1. 设备把 Mac 的 IPv4 地址设为默认网关，普通局域网 ARP 将 Mac IP 解析到其 MAC。
2. BPF 捕获指定设备发给 Mac MAC 地址的 IPv4 TCP/UDP 帧；同网段目标和其他设备的流量被排除。
3. gVisor Netstack 在用户态终止连接，通过普通套接字连接原目标 IP 和端口。
4. 上游套接字使用 `IP_BOUND_IF` 绑定指定 `utun` 出口；绑定失败时拒绝连接，不回退到普通局域网接口。
5. 用户态协议栈生成设备侧回包，经 BPF 发送到先前确认的设备 MAC。

不是以太网透明桥，也不提供热点、DHCP、默认路由广播或局域网全设备接管。转发后的上游连接由 Mac 建立，不能保证保留 P2P 所需的原始 NAT 映射语义。

## 权限与生命周期

GUI 通过 macOS 管理员验证启动监督进程。引擎打开 BPF 后按配置的当前用户降权，再处理数据包。监督进程检查 GUI 身份与存活、局域网配置、出口接口和引擎心跳。

GUI 退出、停止请求或监督进程退出会结束引擎。出口消失或接口索引变化时终止旧引擎，待出口恢复后重新启动；局域网配置变化则停止并要求重新配置设备。没有安装永久 helper 或 launchd 服务。

停止请求使用限制权限且拒绝符号链接的控制文件，停止时无需再次输入管理员密码。

## 为什么使用用户态转发

开发早期的内核转发方案在测试 Mac 上发生过系统崩溃。当前发布版已经完全替换该路径，不使用 PF `route-to`，不写入系统 IP 转发开关，不修改系统路由。旧内核转发命令入口会被拒绝，测试脚本对相关实现进行检查。

这些设计不代表软件不存在缺陷，也不能替代跨系统版本与长期运行验证。当前发布面向已经完成基本通讯验证的用户态方案。

## 监控与域名

统计设备侧 IPv4 包长，包括协议头。每次主动开始转发产生新会话，出口引擎重启保持本次累计。Google 与服务器主动探测不计入设备累计。

域名通过 TLS ClientHello SNI、HTTP Host 和已转发的 DNS A/CNAME 回应被动关联，不进行 TLS 解密或反向 DNS 猜测。TCP 初始观察、DNS 缓存与连接列表均有限额和时效；域名只用于显示，不改变拨号目标。

当前状态中会保存有限的连接元数据用于监控；主动导出的诊断可包含这些地址。程序未提供遥测服务或持久化完整访问历史的功能。

## 开发结构

| 路径 | 用途 |
| --- | --- |
| `Sources/App.swift` | SwiftUI 界面、模型、管理员验证与诊断导出 |
| `Sources/Shared.swift` | 配置、网络接口清单、统计与控制文件 |
| `Sources/Helper.swift` | 权限检测与转发监督 |
| `Relay/main_darwin.go` | BPF、接口绑定、降权与入口 |
| `Relay/engine.go` | 用户态 TCP/UDP 转发 |
| `Relay/health_darwin.go` | 局域网及出口健康检测 |
| `Relay/endpoints.go` / `Relay/names.go` | 连接元数据与被动域名识别 |
| `Tests` / `Relay/*_test.go` | Swift 逻辑和 Go 转发测试 |
| `Assets` | 图标、制作说明与导出脚本 |
| `ThirdParty` / `Relay/vendor` | 固定依赖及其许可 |

参考：[gVisor 网络架构](https://gvisor.dev/docs/user_guide/networking/)、[Apple BPF 头文件](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/net/bpf.h)、[Apple：Packet Filter 不属于应用 API](https://developer.apple.com/documentation/technotes/tn3165-packet-filter-is-not-api)。
